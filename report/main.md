这份报告记录了光线追踪优化和选做题 Mini WorkSteal 的实现与实验。光追主要改了两处：用 OpenMP 并行计算像素，用 BVH 减少求交次数，同时检查图像是否与原版一致。WorkSteal 则围绕一个问题展开：把任务分给更多线程后，什么情况下能更快，什么情况下会多出开销。补充实验和复现方法见文末仓库中的附录。

|项目|最终方案|主要结果|
|---|---|---|
|光线追踪|O3、OpenMP 像素块并行、16 桶 SAH BVH、延后构造命中记录|Render time 中位数 1968.697 → 85.006 秒，耗时比 23.16；六次输出均与参考图逐通道一致|
|WorkSteal|六类策略分别实现；采用 round_robin、immediate、single|细粒度集中布局中，同一程序关闭与开启窃取的 epoch 时间比为 2.55-5.28；粗粒度下收益不稳定|

实验环境为 Intel Core i9-13900HX，Ubuntu 24.04 / WSL1。

# 1 光线追踪的分析与实现

## 1.1 从哪里改起

原版逐像素采样，递归计算光线散射，每次查询场景都要逐个检查物体。我从这两处入手：让不同线程计算不同像素，再用空间结构跳过不可能命中的物体。修改时保留题面规定的采样、散射、天空颜色和随机数规则，main.cpp、common.hpp 和 math/color.* 也保持原样。

## 1.2 按完整像素并行

并行时，我把一个像素的全部样本交给同一个线程。每个像素有独立随机流，这样只调整像素之间的执行顺序，就能保留像素内部的计算和随机数消耗顺序。最终按 16×8 像素块动态分配，chunk 为 1，在本机使用 32 个线程。

输出也要处理：多个线程直接写同一个文件流会互相竞争。因此，各线程先把结果写到对应的像素缓冲，计算结束后再按原行列顺序输出，额外使用约 18.54 MiB 内存。缓冲分配、计算和文件输出都计入 Render time；BVH 在场景初始化时建立，耗时另记。

## 1.3 用 BVH 减少无效求交

BVH 把场景物体分组，再用包围盒组织成树。光线没有碰到一个盒子，就可以跳过里面的物体。我比较了中位数划分和 16 桶 SAH，最后保留后者。SAH 用子盒面积和物体数量估计求交代价，据此选择分组；每个叶子最多放 8 个物体，分桶无法有效划分时再回退到中位数划分。

遍历时先检查入口较近的子树，找到命中后就用这个距离缩小后续范围。这里要注意，BVH 会改变物体的访问顺序，等距命中和盒边界如果处理不同，结果也可能跟着变。因此，我保留了原版的命中选择规则，球体求交仍用 double 和原公式。

## 1.4 延后构造最终命中记录

原版每发现一个候选命中，就计算位置、法线和材质等信息；后面遇到更近的球体时，前面的记录又会被覆盖。我把这部分计算往后放：先比较距离，确定最终命中的球体，再补全记录。这项修改只对 sphere 类型启用，派生类和其他物体仍走原接口。

这一版还把该类型的距离计算改成了直接调用。两项修改放在一起测试，因此下文给出的是它们的组合效果。

LTO、PGO 和 SIMD 也做过比较，最后没有保留。最终版本使用普通 O3 编译，相关结果见在线附录A。

# 2 光线追踪的实验结果

## 2.1 实验设置

按题目要求，图像大小设为 1200×675，每像素采样 200 次，最大深度为 50，seed=42。计时使用程序输出的 Render time，包含渲染和文件输出。原版采用 O2 串行编译，与优化版各运行三次。用 A、B 分别表示原版和优化版，运行顺序为 A1、B1、B2、A2、A3、B3。未额外预热，三次结果全部保留。

|配对|原版 O2 / 秒|最终版 / 秒|原版 / 最终版|
|---|---|---|---|
|1|1897.516|84.857|22.36|
|2|1968.697|85.006|23.16|
|3|1993.332|85.197|23.40|
|中位数|1968.697|85.006|23.16|

![图2 优化前后的渲染耗时](assets/raytracing-comparison.svg)

图2：左图为两组三次运行的中位数，右图为三对运行各自的耗时比，纵轴均从零开始。23.16 为两组中位数之比，是编译选项、算法和线程配置等修改的共同效果。两组数据都在本机测得，未使用题面中 Xeon 的参考时间。

## 2.2 图像质量与单项优化效果

我直接比较原始 PPM 文件，六次输出都与官方参考及同参数原版逐通道一致，MSE=0，PSNR 为无穷大，满足题目 45 dB 的要求。求交部分还单独检查了区间边界、等距命中、特殊方向和派生类型，比较修改前后的距离与命中记录。下表列出 SAH 划分和延后构造命中记录的效果，每个版本测三次，取中位数。

|优化项|优化前 / 秒|优化后 / 秒|耗时降低|
|---|---|---|---|
|中位数 BVH → 16 桶 SAH|113.684|96.265|15.32%|
|即时构造 → 延后构造|97.544|90.667|7.05%|

这两项是在不同实验中测的，加速比不能直接连乘。后续比较时，我采用一个偏保守的办法：新版本三对都更快，而且最慢的一次也快于旧版本最快的一次，才保留修改。这个办法用于筛选方案，没有做统计显著性检验。

## 2.3 耗时波动

还有一个没解决的问题：同一个优化程序，之前测到过 17.435 秒，这次对照却在 85 秒左右。测试用的是日常电脑，没有单独控制 CPU 频率、温度和后台负载，具体是哪一项造成这么大差距，目前还没查明。加速比只根据本次对照计算。WSL1 下没有取得可靠的硬件采样，也暂时分不清求交、缓存和同步各占多少时间。

# 3 Mini WorkSteal 的实现与测试负载

## 3.1 固定任务集与策略接口

这部分我先把范围定为固定任务集：所有任务在执行前创建，不在运行中递归提交子任务。运行时使用持久线程池和带互斥锁的双端队列。这样可以保持各组实验的总工作量相同，也能用剩余任务数判断是否结束，再比较负载均衡、调度开销和局部性。

![图3 运行流程](assets/worksteal-runtime.svg)

图3：各类策略通过接口组合，线程池负责同步和执行，最后由应用核验结果。Migration 在线程队列间转移任务描述符，Affinity 设置工作线程与逻辑 CPU 的绑定。

|策略|职责|代表实现|
|---|---|---|
|Partition|任务切分与粒度|fixed_grain、balanced_chunks|
|Placement|任务初始队列|按 home 或 round_robin 放置|
|Victim|选择窃取目标|round_robin、seeded_random|
|Timing|窃取与空闲等待时机|disabled、immediate、bounded_backoff|
|Migration|单次转移的任务数量|single、capped_half|
|Affinity|配置线程绑定|unbound、显式逻辑 CPU 列表|

每个线程从自己的队尾取任务，空闲时从其他队列的队头窃取。任务把结果写到各自的位置，完成后再通知线程池。测试除了检查结果，还检查任务是否恰好执行一次，以及重复调用、异常恢复和关闭是否正常。为检查扩展接口，我另外加了 test_reverse 策略，只添加实现、注册代码和构建文件，原运行时不需要改动。

## 3.2 工作负载和对照

我用了三类负载：均匀负载看任务切细后会增加多少开销，偏斜负载看空闲线程能否分担工作，重复内存访问则用于观察局部性。输入由 seed 和元素编号确定，改变 grain（每任务元素数）只改变分组，总工作量不变。每次运行后都逐元素重算并检查结果，小规模输入还与独立的 Python 参考实现比较。

实验还包括串行、静态队列和集中队列。检查早先的 off/on 对照时，我发现 off 空闲时等待、on 却使用 yield，测到的差值里也有空闲处理的影响。后来增加了独立的 disabled_yield 策略，让两者都 yield，队列、锁、初始顺序和完成协议保持相同。下文 epoch 指执行时间，不含建队列和完整核验；app 包含初始化和核验。

# 4 任务粒度与窃取收益

## 4.1 均匀负载中的开销对照

为了尽量单独看调度开销，我先只用一个工作线程，固定均匀负载 N=262144、K=16，比较线程池和连续串行循环。三个 grain 都是八路计算内核宽度的整数倍，避免把标量尾部差异带进来。每个条件测五次，表中为中位数。

|配置|任务数|epoch / ms|相对连续串行|
|---|---|---|---|
|连续串行|单次连续循环|2.3888|1.000|
|线程池 grain=4096|64|2.3769|0.995|
|线程池 grain=64|4096|2.5319|1.060|
|线程池 grain=8|32768|2.8658|1.200|

grain 从 4096 减到 8，任务数从 64 增至 32768，epoch 多了 0.4889 毫秒（20.6%）。工作量相同，任务变多后，取任务、函数分发和完成通知也更频繁，这些成本合在一起体现为时间差。粗粒度与连续循环很接近，单次又只有几毫秒，我没有据此给它们排高低，也没有把差值换算成每把锁的耗时。

## 4.2 偏斜布局与不可拆大任务

接着用偏斜负载观察窃取能否分担工作。补测使用同一个程序、16 个工作线程和 K=256，换两个新输入，每种布局和粒度做 5 对 off/on 比较，两者空闲时都 yield。集中布局四组都是 5/5 对开启窃取更快，epoch 中位数时间比为 2.55-5.28；分散布局为 1.26-1.83。

![图4 相同空闲策略下的窃取收益](assets/worksteal-matched.svg)

图4：按输入 seed 分为两个子图，柱高为 off 中位数 / on 中位数；大于 1 表示开启窃取更快，虚线表示两者相等。每个条件测五次，输入规模分别为 65536 和 98304。

但任务切得太大时，窃取也帮不上多少忙。另一次实验中，grain=16384 时只形成 4 个和 6 个任务，最大任务占总计算量的 62.5% 和 58.33%，没有测到稳定收益：已经执行的大任务不能再拆，换 victim 也分不走其中的工作。这里的计算量按 mix 迭代次数估计，不直接等于实际耗时；app 的改善还要另看，不能套用 epoch 的时间比。

# 5 局部性与最终策略选择

## 5.1 预读线程与局部性

系统显示 LLC 约为 36 MiB。补测固定执行线程，比较由它自己或另一个线程预读数据。64 个任务的总数据分别为 512 KiB、4.5 MiB 和 288 MiB，每任务为 8 KiB、72 KiB 和 4.5 MiB，每个条件测五次。下表耗时比为“另一线程预读 / 执行线程预读”。

|总数据|执行0 耗时比|执行1 耗时比|成功窃取次数|
|---|---|---|---|
|512 KiB|1.021|0.956|46|
|4.5 MiB|1.007|1.002|47|
|288 MiB|1.019|0.974|48|

最后一列是另做的四线程窃取诊断，三种规模分别有 46、47、48 个任务由非 home 线程执行，确实发生了窃取。但固定执行线程后，换谁预读并没有一致的变慢趋势。WSL1 下还没确认物理缓存映射，也没有可靠 PMU，所以这组差异只能说明预读线程变化后的表现，不能当作纯缓存损失，更不能说明局部性没有代价。负载均衡、调度和局部性还可能相互影响，不能直接相加。

上表最大的单任务只有 4.5 MiB，还不够覆盖题面要求的大任务。因此又测了每任务 288 MiB、共四任务的情况。诊断有 3/4 个任务由其他线程执行；固定执行线程后的两个预读耗时比分别为 1.009 和 0.988，同样没有一致的变慢趋势。

## 5.2 一次窃取多个任务

一次多取几个任务，可以少跑几趟其他队列，但多取是否一定更快，还要看实验。我固定程序、线程数、粒度和输入，比较 single 与最多取 4、16、64 个任务的方案。cap4 初测较快，于是换两个输入，各做 7 对比较。下表是集中布局的结果。

|输入 seed|epoch single→cap4 ms|更快对数|app single→cap4 ms|
|---|---|---|---|
|116009|3.7183 → 3.6328|3/7|31.6320 → 30.2063|
|122011|5.0438 → 5.1210|4/7|38.1532 → 41.2096|

cap4 初测让 epoch 下降约 22.7%，换输入后却只有 3/7、4/7 对更快，第二组 app 中位数还增加了 8.01%。诊断里，成功窃取次数确实少了，成本分配也更均衡，但搬走的描述符总量增加了。这两组的收益不稳定，我最终保留了 single。

## 5.3 最终配置

比较这些方案后，我保留 fixed_grain、round_robin victim、immediate 和 single，并指定线程绑定的逻辑 CPU。初始任务怎么分由 placement 和 layout 决定，线程数和粒度按负载调整，具体配置见在线附录B。

完整核验并行化和内存内核调整的结果见在线附录A。这些修改改善的是应用中的其他环节，不能都算作工作窃取带来的加速。

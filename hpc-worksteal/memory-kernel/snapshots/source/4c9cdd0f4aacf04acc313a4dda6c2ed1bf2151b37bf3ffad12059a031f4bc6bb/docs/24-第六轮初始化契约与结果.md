## 接口与线程生命周期

`measurement.initialization_workers`可省略，默认1；仅整数1..128合法。它只控制memory数据填充，不改变执行Pool的worker数或参考核验线程数。结果新增`initialization.requested_workers`、`workers_used`和scope；这些设置不混入工作负载身份。compute实际使用0个填充线程，空memory同样为0。

先保留控制线程上的vector分配与清零，再按完整连续元素块划分数据。active=min(请求线程数,N)，前N%active个分块各多一个元素；每个word仍按原全局下标计算`mix(seed+index)`，使用uint64自然回绕。active≤1走原连续循环。各线程独占区间，没有共享写入游标；全部join后才计算身份、创建Pool、进行原home预读及执行。

填充闭包、active及成员数据的生命周期长于jthread容器。创建线程抛异常时，已创建的jthread先析构并join，再销毁所引用的局部变量及成员。填充体只有算术与独占写入，不分配、不主动抛异常。没有注入线程创建失败，异常路径依据RAII语义，而非故障注入证据。

原计算递推、完整独立标量参考核验及逐字节顺序FNV均保留。分配、清零、生成、线程创建/join仍计入workload_initialization和app；epoch边界不变。app沿用run()内部从配置处理至Pool关闭的计时，不包含外层配置文件读取、返回JSON构造/序列化、之后的工作负载析构及OS进程启动；完整进程另记process耗时。

## 从负结果得到的下一步

初始化区间中位数仅31.896→29.581ms、49.299→45.434ms，约下降7.3%/7.8%；它包含原控制线程清零与线程创建/join，不能据此单独推断生成器的扩展效率。身份散列仍约34.5/52.2ms，接近各候选app中位数的39%；这些不同区间的中位数不能相加当作一次运行。

候选epoch中位数反而6.850→7.879ms、8.417→9.149ms；不能声称计算或工作窃取更快，也不能仅凭阶段相关性断言是缓存迁移导致。继续增加初始化线程没有本轮证据支持。下一轮若分析散列/数据布局，应先在保持顺序FNV逐字节完全一致、保留完整参考核验的前提下另立协议；若研究题目核心调度机制，应回到epoch及S3-off/on，而非用初始化收益替代。

初始化线程继承控制线程掩码，不承诺物理绑核。主线程清零与逻辑home预读保留，但并行填充可能改变缓存状态；本轮测的是包含这些影响的应用干预。Windows起始CPU门禁和WSL批中观测只能证明通过已定义的观测条件，不能证明物理独占、P/E/SMT分配或缓存因果。

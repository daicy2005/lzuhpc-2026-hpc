# 工作负载与机制对照

> 下文为执行前机制设计，具体实现可能按 docs/12 调整。已测工作集、零偷取诊断和因果边界见 [最终评审与选择](13-最终评审与选择.md)，不能把计划项当成果。

状态：设计已细化，尚未实现、校准或运行。本文固定逻辑语义；具体源码/输入生成器版本在首个真实batch前快照。

## 1. 公共身份与工作量

ElementId标识不可再拆的逻辑元素，TaskId标识本次Partition产生的区间，worker只是本次执行者。改变grain会改变TaskId/区间，但不得改变ElementId的输入、成本和结果。初始队列排列只移动已有TaskId，不重写区间或重新生成成本。

compute输入按seed与ElementId确定性生成uint64初值；每元素执行cost[i]次有状态的整数混合，回绕为uint64定义行为。热循环采用同一共享内核，结果写output[i]并逐元素与串行参考比对。精确公式、常数与已知小向量在P1实现时冻结；本文不提前宣称已验证哪种内核。

避免无符号外的未定义溢出、时间依赖RNG、sleep伪装计算、共享原子累加结果。内核不能被简化为未消费结果的空循环；反汇编可作辅助检查，不单凭“有循环”证明计时有效。

总逻辑成本W_units=sum(cost[i])、每task成本为所含元素成本之和、Cmax_units=max(task_cost)。这些是确定性工作单位，不是每元素真实等时保证，尤其不能在混合CPU上直接换算成秒。理想同速处理器的max(W/p,Cmax)用于解释不可分任务限制，不当硬件实测下界。

保存元素生成参数、成本表hash、task区间hash、初始队列hash、逐元素输出hash。hash用于追溯；真正正确性检查逐元素进行，不能只凭一个checksum证明所有任务恰好一次。诊断覆盖计数单独检查任务ID不丢不重。

## 2. W01 均匀计算与粒度

cost[i]=K，N和K在每个batch中不变。grain只将[0,N)拆成长度g的连续段，尾段合法。S0直接调用同一内核处理[0,N)，其结果对全部grain通用，不把S0按grain重复统计。

粒度变化必然改变task描述符数量、队列内存、同步次数以及邻近输出的共享缓存行行为；它们均属执行方式的费用，不声称W01完全没有访存或假共享。记录输出/成本表/描述符估计字节和实际task_count。

S1/S3-off/on在同p/g使用相同初始TaskId列表。S1与S3不要求相同内部实现；S3-off/on则必须保持同队列锁、本地LIFO和完成协议，disabled分支只禁止跨worker取得任务。S2可按统一TaskId序列入共享队列；其取得顺序差异如实披露。

空任务微实验只能作辅助诊断，不替代有真实计算、可核验输出的W01。每task原子完成更新的竞争是可疑机制之一，首次不在开关窃取时同时修改完成协议。

## 3. W02 固定成本集合，改变初始不均衡

冻结N、grain、p与cost表：令预定部分元素为重元素（例如1/8成本为9K，其余K，总成本在N可整除时为2NK）；重元素身份按固定分块/seed生成并保留，不随排列变化。具体比例在W02执行前冻结。均匀2K成本组可作另一类工作负载，不与偏斜组当成相同输入求算法比值。

先形成固定task集合，再生成三种初始队列方案：

| 方案 | 构造 | 目的 |
|---|---|---|
| concentrated | 让高成本task集中在少量队列，保持每队列任务数量可比 | 可解释的合成压力场景，不作为唯一成绩 |
| spread | 按确定规则分散重任务，记录规则和每队列成本 | 接近已均衡分配，观察额外窃取成本 |
| shuffled | 按预定seed排列TaskId再分配 | 检查人工压力场景外的行为 |

三种方案的task集合、W_units和参考输出完全相同；每方案保存每worker初始任务数/成本单位和队列实际顺序。改变放置也会改变局部执行顺序，属于已声明的初始布局变化，不能装作只改了抽象“均衡度”。对同一初始方案比较S3-off/on时列表逐字节一致。

诊断至少报告：实际转移/执行归属、每worker完成成本单位、first_start/last_finish（相对t0）、计算/等待等互斥状态区间。可用mean(work_units)/max(work_units)描述工作分布，但不把它当真实CPU利用率；不同worker速度、Cmax和调度成本仍影响完成时间。

不预先强迫S3一定偷到任务；没有偷取则这一配置不提供迁移效果证据，但仍保留timing。若设计失去区分度，先记录pilot，再为后续新batch调整参数，不改已封存输入。

## 4. W03a 受控访问

先在两个已验证不同逻辑CPU的worker上进行；没有物理映射依据时只称不同worker/逻辑CPU，不称不同物理核或NUMA域。工作负载为固定只读uint64数据块、固定顺序/遍数的访问与局部checksum，最终逐块核验。

同一进程内由home worker进行固定页预触碰及预读，所有条件执行同一预处理；预处理读的checksum单列，计时仍完整重新读取计算，不缓存最终结果。计时阶段由home或指定另一worker访问同一块、相同遍数，其他worker等待。每次重复新进程重新初始化，home0→执行1和home1→执行0在执行前安排对称对照，帮助识别worker速度差异。

不以“预读过”声称命中某级cache，也不主动清空系统缓存或其他用户进程数据。预处理到执行的同步和等待按相同窗口记录；工作集大时预读不能使全部数据同时驻留，这正是需要测的条件。

## 5. W03b 动态迁移与局部性窗口

只读数据块具有固定BlockId和home，不随grain或结果重算。比较S3-off/on以及single/capped_half时固定task划分、逻辑数据块/访问偏移集合、布局与对齐、home、预触碰方式、初始队列与绑核；不要求不同进程虚拟地址相同，也不关闭系统ASLR来追求此条件。需要不同工作集时属于新的规模组，不能跨规模相减当精确局部性费用。

单task工作集、每worker活跃工作集、总活跃工作集三项都记录。若仅总和远大于LLC、每task仍很小，不能声称满足“任务远大于LLC”端点。大量独立大块可能超过内存预算；先限制并发worker/任务并冻结新矩阵，不用swap获得虚假的缓存曲线。

连续访问重复主要研究复用，另可预定无复用对照；改变访问模式要明确拆组。局部checksum和结果存储避免多线程共享累加；结果数组的假共享属于另一个潜在因素，不伪装为数据迁移。

真实执行记录steal成功、执行者/home不匹配及访问字节口径。home不匹配可以证明逻辑迁移，不能直接证明cache miss；即便不同worker，也可能共享LLC。无PMU时结论止于条件下的耗时/迁移关联和W03a支持，不写已精确测得缓存损失多少秒。

## 6. 推断边界

固定工作/同框架对照比跨框架快慢更能解释机制，但仍有线程速度、频率、输出访存、锁、完成计数及观测开销交互。诊断跟踪是另一构建或模式，不能逐段减去timing数据。三效应不被强制拆成三个可加的独立常数。

每个实验先给假设、可能反例和失败时如何解释；局部性接近零、不均衡场景偷取仍不划算、均衡场景动态调度反而慢，都属于有效发现。

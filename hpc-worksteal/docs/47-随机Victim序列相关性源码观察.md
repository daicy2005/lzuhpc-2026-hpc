# 随机victim：同序号相关性与下一步边界

2026-10-25，第十六轮资源等待期间的只读源码观察，尚未观察第十六轮正式计时。此文不修改冻结协议45、采集器或候选，不构成新的采用结论。

## 核实的源码性质

以第十六轮原测量源码`e85c97b09468b4a3c6a6286bdceac7ffa408d2983cc2a957765e6b3bd9580c86`为准：src/runtime/worker_pool.cpp在每个worker的每个epoch设`rng=0`；src/policies/register_defaults.cpp中seeded_random计算`v=mix(++state+seed)%(p-1)`，再通过`v>=me ? v+1 : v`跳过自身。生成候选索引时没有混入worker编号。

因此，在p32/seed17且各worker处于相同尝试序号的条件下，所有worker先得到同一个压缩索引，再因排除自身映射到至多两个真实victim。独立Python按原uint64 mix计算前四个序号：

|零起始尝试序号|压缩索引|映射后的victim与worker数|
|---:|---:|---|
|0|7|victim7：24；victim8：8|
|1|0|victim0：31；victim1：1|
|2|22|victim22：9；victim23：23|
|3|23|victim23：8；victim24：24|

这是确定性的源码性质，不是一次实际运行的事件轨迹。worker可能在不同时间耗尽本地任务、处于不同尝试序号，不能据表声称32线程同时争锁，也不能据此解释尚未采集的快慢。相同seed保证可复现不等于worker序列互相独立；round_robin的起点本来就包含me。

## 还有价值的后续候选

若继续扩展，优先考虑把worker编号纳入确定性生成的独立victim策略，或每个worker各自循环覆盖其他worker的置换扫描。前者减少相同计数的序列相关性，但仍可能重复探测；后者在每轮访问完其他worker前不重复，但要计算置换且可能有额外费用。两者都不保证更快，也不根据本表指定初始重队列。

必须新建实现与注册文件、独立构建清单项，不改原Random或运行时；先检查p1/p2、任意p、排除自身、线程状态隔离、确定性和完整覆盖（若宣称），再跑完整runtime/CLI/扩展与实际sanitizer检查。正式比较需另冻协议、新二进制同构建对照、新输入确认，并保留既有第十六轮结果。不在第十六轮失败后追加第三候选或把它作为本轮第二次机会。

目前仍优先完成第十六轮既定采样和交付，以及局部性动态迁移的可辨识实验。无锁队列、拓扑感知或基于队列长度的选择需要额外接口/同步设计，不因随机序列观察就自动引入。

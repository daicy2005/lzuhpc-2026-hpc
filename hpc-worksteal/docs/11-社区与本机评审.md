# 实验方案评审：社区依据与本机条件

> 本文保留 2026-10-15 的 review_only 快照。后续已实施并完成计划实验；更新后的环境、独立终审和策略选择见 docs/12、[最终评审与选择](13-最终评审与选择.md)。

日期：2026-10-15（Asia/Shanghai）。状态：**review_only，未运行性能实验**。

本轮按用户要求，由实验设计、社区资料、本机能力三个子 agent 独立检查并交叉讨论，主 agent 复核项目契约和六份来源。只新增本评审与阅读入口；没有改变首批矩阵、安装工具、实现运行时或启动计时负载。下述“建议”尚不是已冻结的执行配置。

## 1. 总体判断

继续以“固定总工作量，任务粒度和初始不均衡怎样影响窃取收益”为主线。现有固定独立任务、带锁队列、S3-off/on 对照适合 CS149 学习和机制解释，无需先实现无锁队列、递归任务树或完整通用调度框架。

首批仍限定 W00/W01，最多 25 个计时条件、147 个进程和 900 秒批次预算。这里都是未来上限，没有实际完成次数。首批只回答粒度与框架费用、从 1 到 p0 个 worker 的净变化；只有两个线程数，不能定位扩展饱和点，三个 grain 也不能保证覆盖最佳粒度。

本机当前适合推进实现与能力检查；通过前置验收后，可作有限的逻辑线程预试验。尚不足以宣称四物理核扩展、精确缓存迁移损失或跨平台最佳策略。

## 2. 社区依据：借鉴什么，不能照搬什么

以下正文在本轮实际访问成功。它们是机制与方法依据，不是本项目的已实现功能或性能证据；链接中的 master/main 为可变版本。

| 来源 | 核查到的内容 | 对我们的意义 |
|---|---|---|
| [oneTBB：How Task Scheduler Works](https://raw.githubusercontent.com/uxlfoundation/oneTBB/master/doc/main/tbb_userguide/How_Task_Scheduler_Works.rst) | owner 执行新任务、thief 偷旧任务；在其任务生成模型中关联深度优先与临时广度优先 | 保留双端规则，但我们没有递归 spawn 树，不能声称偷到的是更上层、更粗任务，或天然保证局部性 |
| [oneTBB：Controlling Chunking](https://raw.githubusercontent.com/uxlfoundation/oneTBB/master/doc/main/tbb_userguide/Controlling_Chunking_os.rst) | 太小的 chunk 增加调度费用，太大则可并行块不足；给出约 100,000 周期的经验建议 | 支持固定工作扫 grain；100k 周期不是本项目阈值，grain=1/64/4096 只是预定探针 |
| [oneTBB：Bandwidth and Cache Affinity](https://raw.githubusercontent.com/uxlfoundation/oneTBB/master/doc/main/tbb_userguide/Bandwidth_and_Cache_Affinity_os.rst) | 重复访问、计算/访问比例及数据能否适配缓存影响 affinity 收益 | 支持 W03a/b 分层；home 不是缓存所有权，0.125/1/8 LLC 是自选覆盖尺度，非社区通用定律 |
| [Google Benchmark：User Guide](https://raw.githubusercontent.com/google/benchmark/main/docs/user_guide.md) | 内部启动工作线程时，主线程 CPU 时间可能不代表工作；wall time 与 process CPU time 意义不同；DoNotOptimize 不阻止所有常量折叠 | epoch wall 作为主指标合理；若记录累计 CPU 时间应分列。仍须消费输出、逐元素核验与检查内核，不能靠一个防优化标记担保 |
| [Google Benchmark：Random Interleaving](https://raw.githubusercontent.com/google/benchmark/main/docs/random_interleaving.md) | 交错重复可降低运行间变化 | 支持预生成并保存执行顺序；固定随机 seed 不等于位置严格平衡，也不保证本机一定降低某个比例的噪声 |
| [Blumofe／USENIX：The Cilk language and work-stealing scheduler](https://www.usenix.org/legacy/publications/library/proceedings/ana97/full_papers/blumofe/blumofe_html/node2.html) | 随机 victim、双端操作及 well-structured 依赖模型是其调度分析背景 | 不能把 T1/P + T∞ 直接写成本项目 round_robin、带锁 flat 队列的性能保证；理想同速处理器 max(W/p,Cmax) 仅用于理解不可分任务 |

当前不增加 oneTBB/Taskflow 外部运行时排名：它们有不同功能和实现，不能替代我们的同框架开关对照，且会增加首批依赖与解释负担。以后若增加，仅作为单独声明的整体实现比较。

## 3. 实机证据与能力边界

以下为本轮只读检查快照，不是持续监测。Windows 为 i9-13900HX，CIM 报告 24 核、32 逻辑处理器。

| 检查项 | 当前事实 | 实验限制 |
|---|---|---|
| Linux | HPC-Ubuntu-24.04，WSL1；Ubuntu 24.04.5，kernel 4.4.0-26100-Microsoft | 结果属于这个兼容环境，不能视为裸机 Linux 或 WSL2 的结果 |
| 可用逻辑 CPU | /proc/self/status、taskset 报告 0–31 | 仍需逐 worker 检查绑定调用返回值与实际掩码 |
| 前四个 CPU | Linux 报告 cpu0/1 为 core0、siblings=0-1；cpu2/3 为 core1、siblings=2-3 | 按该报告是两组 SMT；尚未独立对齐 Windows 物理编号，更不能猜 P/E 核映射 |
| cache | Linux cpu0/cache 目录缺失；Windows CIM 报告 L2=32768 KB、L3=36864 KB | 容量字段不足以确认 worker 的 LLC 共享域；当前不能据此声称题面 LLC 两端已覆盖 |
| 工具链 | G++ 13.3、Python 3.12、make 可用；cmake/ninja/clang++ 未找到 | CMake 构建路径待补齐；Ninja、Clang 并非必须同时安装 |
| PMU | perf 未找到；event_source/devices 与 perf_event_paranoid 接口不存在 | 分开记录工具缺失与接口缺失；未做 perf 运行验证，不宣称已通过或已穷尽所有支持路径 |
| TSan | GCC 13 的 libtsan 库文件存在 | 没有本项目真实运行通过证据；库存在不代表能运行，也不代表不可用 |
| 并发任务 | 查询时未见光追/WorkSteal 活动进程 | 只是瞬时筛查，开跑前必须再核对 |
| 主机负载 | Windows 总 CPU 负载单次快照为 47% | 不能称机器空闲或独占，不能用这个数推断持续负载 |

因此保留现有 first-four 规则只适合作为明确标注的逻辑 CPU 预试验。正式扩展实验另立计划：先核对物理核心、SMT、效率类别及可用集合，再冻结 CPU 列表；不能测很多列表后选最快一组。

W03 的硬件缓存归因暂缓。可以先完善 workload 和记录逻辑迁移，但最终题面要求的可信 LLC 两端覆盖仍需补齐；“当前证据不够”不能变成免做该项。PMU 不是 W00/W01 的硬前提。

## 4. 评审意见的取舍

| 建议 | 主审结论 | 后续落点 |
|---|---|---|
| 补 owner/thief 两端 | 部分重复：docs/02 已明确 owner 后端取、thief 前端取 | 保留现有方向；补物理入队顺序与批次内部顺序，不写成已有契约缺失 |
| 冻结锁忙语义 | 接受 | P3 前明确阻塞 lock 或 try_lock；建议先固定 try_lock，busy/empty 分开诊断。取锁失败不等于全局无任务，重试/等待仍须满足终止与唤醒契约 |
| 明确任务顺序 | 接受 | 规定初始 push 次序、S1 遍历方向、S2 出队方向及批量迁移后 owner 的实际取得次序；保存实际列表与版本。首批 single 迁移无需加新条件 |
| 明确控制线程 | 接受 | 并行模式统一阻塞等待完成，记录主线程实际掩码、是否与 worker 共用 CPU。计时包含主线程唤醒延迟，不把其时间称纯内核执行时间 |
| 检查热写元数据布局 | 接受，限于实施说明 | 记录完成原子及 worker 统计布局，避免无意的统计假共享。保留初版完成协议；不在窃取开关实验中同时更换协议 |
| 用更多线程点解决扩展问题 | 首批不采纳 | docs/10 的交付措辞应收窄为 1→p0 净变化；完整曲线留给后续冻结计划 |
| 增加 grain64 诊断 | 首批不采纳 | 保留最多四次端点诊断；grain64 进入 W02 时，在 W02 计划中安排覆盖与实际迁移诊断 |
| 固定 seed 即严格平衡 | 不接受该等同关系 | 编排器保存实际顺序并检查位置分散；三次 timing 不声称四种模式的每个位置出现次数严格相等 |
| 将 W02 称为纯不均衡效应 | 不接受 | 初始放置同时改变执行顺序，现有 docs/09 已承认；同布局 S3-off/on 才是主要净效果对照 |

这些建议不改变“成功的慢样本也保留”“诊断与计时分开”“三效应不可直接相加”的既有规则。WSL、SMT、全局完成原子、输出假共享等都会影响实测，不能把细粒度退化全部归因于 deque 锁或窃取。

## 5. 把目标落成可量化问题

后续真实计划应事先声明比较式，而不是跑完再挑定义。以下是建议口径，尚无数值：

| 阶段 | 主比较 | 能解释什么 |
|---|---|---|
| W01 | 固定 p/grain 的 T(S3-off)/T(S3-on)；同总工作下各 grain 的 epoch 与端到端 | 均匀任务上允许窃取的净效果，以及粒度/框架费用的合并表现 |
| W02 | 每个固定初始布局内的 T(off)/T(on)，结合尾部时刻与每 worker 成本分布 | 该布局下开启窃取的净收益；它包含调度费用，不能命名为纯均衡收益 |
| W03a | 同工作集、同访问遍数的 foreign/home 时间比值或差值，两个方向对照 | 受控执行者变化的时间差；线程速度与共享缓存等仍需解释 |
| W03b | 固定划分/home/预处理下的 off/on 与少量迁移策略比较，辅以实际转移诊断 | 动态调度中的迁移与时间关系；没有硬件证据不精确换算 cache miss 损失 |

比值大于 1 的方向需在图表中写清。上述条件效应相互作用，不能相加还原总耗时。首批 3 次用于初筛，确认 5 次及工程门槛也不是统计显著性保证。

## 6. 推荐推进顺序

1. P1：补齐 CMake 构建路径，冻结确定性内核与小参考向量，实现串行、输出核验、计时/归档骨架；验证普通构建和 ASan/UBSan，实际检查 TSan 能力。
2. P2/P3：实现静态、集中队列、带锁工作窃取及 off/on；先冻结本节指出的顺序、锁忙、控制线程与布局契约，通过覆盖、终止、异常/关闭、亲和性及新增策略扩展验收。
3. 生成真实首批计划：复核主机负载与冲突任务，明确逻辑 CPU 预试验标签，保存实际顺序并执行有界校准；此时才冻结 K 和 plan，开始 W00/W01。
4. 根据有限筛选证据单独设计 W02；以后再补可信拓扑/LLC 与 W03。无显著收益、没有发生窃取或缓存效应接近零均如实报告，不追跑到好看为止。

当前项目仍处于文档和方案阶段。这轮得到的是经社区资料和实机条件校验的建议，没有可报告的加速比，也没有已完成的运行时正确性验收。

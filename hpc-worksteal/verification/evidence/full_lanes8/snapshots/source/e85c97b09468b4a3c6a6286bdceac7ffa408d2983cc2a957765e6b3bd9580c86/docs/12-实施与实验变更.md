## 当前实施约定

- 持久 worker、condition_variable 启动门；主线程持状态锁记 t0，发布 generation，再阻塞等待 finished；t1 在确认完成后读取。线程创建/销毁在 epoch 外并纳入端到端。
- seq_cst remaining RMW 串联完成发布，最后 worker 在状态锁下置 finished；主线程还等待全部 worker 返回屏障后才能开始下一 epoch。异常取消未开始任务、等待已运行任务、向调用方抛出；pool 可恢复运行新 epoch。
- TaskId 升序 push_back，本地 pop_back；静态对照也反向遍历其列表。集中队列 TaskId 升序 pop_front。victim 用 try_lock，busy 与 empty 在诊断分列。
- 迁移先取队列长度快照，锁外调用策略，再取锁裁剪实际可用数量；不在队列锁下调用策略或执行任务。批次按 victim 前端移出，第一个立即执行，其余逆序 push_back，故本地连续取得时保留偷出顺序（其他窃取可能交错）。
- 所有并行模式主线程保持进程原允许掩码并阻塞等待，不额外预留核心；worker 记录绑定请求和实际返回掩码。元数据按 64 字节边界分隔；这不等于所有硬件均为 64 字节缓存行。
- memory_reuse 在同进程中按 home 的本地队列做预读，禁用该阶段窃取；完成预读后再正式计时。完整 data hash 在预读前生成，避免 hash 扰动预读状态。引用预读不保证 cache hit。
- 运行时不识别策略名称。注册表通过独立测试注册文件加入 test_reverse，新可执行入口复用核心，构建源显式加入。策略 callback 要求非阻塞、无共享可变状态。

## 已发现的环境限制

WSL1 接受单 CPU 掩码且可读回，但逐逻辑 CPU 的 CPUID x2APIC 并未稳定一一映射。因此掩码核验不能升级为物理驻留保证，正式结果必须写“本 WSL1 环境的逻辑掩码预试验”，不能将 sysfs SMT 表或 CPUID 暂态采样当 P/E 核映射。

CPUID leaf4 每次采样均报告 37,748,736 字节（36 MiB）LLC，与 Windows CIM 的 36,864 KB 交叉吻合。该容量可用于按绝对字节覆盖远小/远大规模，不能证明每 worker 私有缓存内容或稳定共享域；硬件 cache miss 因果归因仍受限。

## 开发校准记录的限制

开发中曾一次性查看 K=64/256/1024（输出正确，S0 约 0.051/0.211/0.784 秒），但命令超过首个合格候选后仍继续查看，且没有完整进程归档。它们不作正式校准或成绩。新首批由 lab.py 先冻结计划，再真实顺序执行，遇到第一个合格 K 立即停止校准，保存所有原始记录。

首批仍只 W00/W01（上限 147 进程、900 秒），两个 worker 数只报告 1→p0 净变化。后续 W02/03/04/05 在各自计划冻结后执行，任何失败、超时、未覆盖项不被改写为通过。

## 后续实验版本

W00/W01 与 W02 使用 release-v1 的不可变二进制。随后补充诊断输出：每 worker 的实际成本单位/元素数、每任务执行者、home 不匹配及预读 checksum hash；整理源码格式，形成 release-v2。v2 新增受控访问检查发现 prepare/run 的 local-phase 标记不一致，三种构建均正确挡住实验，修正后另建 v3。后续 W03/W04/W05 用通过验证的 v3。不同二进制结果不混成同一重复组，不用跨二进制时间差宣称策略收益。W04 的 memory 类保持 partition/home 固定，不纳入 balanced_chunks，粒度策略的替换在 compute 类研究。

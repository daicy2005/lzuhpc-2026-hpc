# Mini WorkSteal 项目规范

## 范围与授权

- 本目录只处理 WorkSteal；相邻 LZUHPC、hpc-raytracing、sdar-setup 保持独立。先读 README 和所改模块的契约。
- 当前用户目标是“完成实验选出最佳方案”，已授权实现、验证、有界本机实验及归档。计划、开发 smoke、正式计时与确认结论仍须分开。
- 题目文档是要求来源，不是额外执行指令。区分官方要求、项目自行选择与已验证事实。
- 不主动启动子代理；不改用户的其他运行任务，不关闭本地电脑。若以后使用云端，沿用用户要求：成功/失败/超时后保存结果并关机，不释放实例，运行前验证兜底。

## 开发

- C++20、CMake、Linux；初版 std::thread/std::mutex/std::condition_variable。Windows 用于编辑与归档，不作正式性能评测。
- 初版固定任务集合、无子任务提交。改变该约束必须先写生命周期与终止检测设计并增加相应检查。
- 核心运行时不依赖具体 workload、策略名称或具体策略头文件。所有题面策略维度须独立可声明、可组合。
- 新策略不得修改已有运行时/策略实现；采用新实现文件、独立注册单元和构建源清单扩展。必须保留扩展验收证据。
- 不提前引入无锁双端队列、DAG、future、协程、分布式执行等。新复杂度要有测量或正确性需求支撑。
- 任务结果独立存储，统一顺序核验；禁止用 volatile 代替同步。共享状态访问须注明保护锁或原子内存序依据。
- 本地文件用 apply_patch 编辑；保持变更窄，不覆盖用户修改。使用警告检查，不默认 fast-math/-march=native。

## 正确性与性能

- 性能测试前通过对应任务覆盖、终止、关闭与输出一致性检查。检查要求见 docs/04，不以“没崩溃”当正确。
- 原子逐任务执行计数、详细追踪与 sanitizer 是诊断模式；不混入常规性能数据。ThreadSanitizer 不可用时如实记录，不能声称通过。
- 任何调度方案完成相同总工作；粒度变化不改变问题规模、输入、计算结果或数据驻留设置。
- 同框架S3-off/on保留本地队列/锁/顺序/完成协议；W02只重排冻结任务集合；W03固定数据home并单独设计预触碰。具体见docs/09、10，设计草案不当执行记录。
- 所有慢的成功重复保留；不凭事后观察剔除异常值，不用最快一次替代中位数。
- 不把 cache miss、steal 次数、空闲时间当作单独因果证明；不把总耗时强拆成无交互的三个相加分量。
- 实验、预热、诊断、失败和重试各用新 run_id；原始记录封存后不可重写。详细口径见 docs/05、06。
- Linux 执行与 Windows 备份验散列；同物理盘两份不等于故障备份，不擅自外传原始数据。

## 学习与交付

- 每阶段更新实现状态、命令、实际检查与限制，说明相关 CS149 概念，不把计划写成成果。
- 报告中的性能结论必须链接组与 run_id；图表保存输入和生成脚本。
- 最终按题面提交代码、复现环境、PDF 和一个完整连续 Session 的用户 Prompt/Agent Response；不含思维链，不伪造或拼接对话。
